# Website and verifier audit — 2026-09-07

## Outcome

The initial 66 tests passed, but they did not exercise several failure modes
in production admission and publication. The audit added regression coverage
and fixed the issues below. This is a code and operational review, not a claim
that every possible sandbox exploit or novel mathematical proof has been ruled out.

## Fixed findings

| Finding | Fix / evidence |
| --- | --- |
| Verifier image identity differed from the website's publication fingerprint | A live, root-side read-only E2B probe confirmed a mismatch. Uploads now check actual sealed image bytes before source upload or quota consumption. |
| Image substituted `e2b/runtime/package*.json` for the repository manifests used by publication | Keep the minimal dependencies installed, then copy the authentic repository manifests into the attested paths. |
| Noncompetitive positive replay checked score but skipped full publication attestation validation | Check exact source digest, author, attribution, upstream, theorem set, axiom policy, and both material fingerprints. A mismatch is terminal infrastructure failure, not endless polling. |
| Lost acknowledgement of successful GitHub queue CAS could kill an admitted sandbox | Reconcile the immutable commit and its ancestry; preserve the worker if acknowledgement remains uncertain. Regression tests simulate commit-then-disconnect. |
| Operator recovery had the same lost-acknowledgement cleanup risk and rejected CLI deployment identities | Preserve both workers until reconciliation, accept the exact-SHA CLI fallback, and give recovery the same 300-second staging budget. Three route regressions cover success, uncertainty, and ordinary failure cleanup. |
| Queue retries trusted job ID without checking the remaining identity | Require matching owner, record name, digest, and sandbox. |
| GCM decryption accepted shortened authentication tags | Require canonical 12-byte nonces and 16-byte tags; specify the full authentication-tag length to Node. A failing regression reproduced acceptance of truncated tags before the fix. |
| Request size was enforced only through an optional `Content-Length` header | Bound the actual request stream to 4 MB, cancel oversized streams, reject invalid UTF-8, and retain the separate 2 MB decoded-source bound. |
| Admission function lifetime was shorter than its possible upload plus durable-write operations | Increase admission route limit to 300 seconds. |
| A concurrent finalizer could delete E2B and make another poll display “expired” after successful judgment | Re-read the durable receipt on sandbox disappearance. A regression covers a promoted receipt racing with cleanup. |
| Sweep could claim `expired-advanced` after the durable queue update failed | Return a retryable non-success response until the update succeeds. |

| Participate terminal example widened the mobile page | Allow grid columns and cards to shrink, preserving horizontal scrolling inside code blocks. |

## Authentication and repeatable end-to-end test

Submission APIs also accept a GitHub personal token, verified through GitHub's
authenticated `/user` endpoint on every request. The token is not retained,
logged, or sent to E2B. The body cannot override authenticated authorship.
Use a dedicated fine-grained token with no repository permissions. Browser
OAuth remains unchanged; an API-token test is not evidence of browser OAuth success.

The E2B template administration endpoint can additionally authorize an explicitly
configured immutable numeric GitHub user ID (`E2B_TEMPLATE_ADMIN_GITHUB_ID`).
It remains closed by default. Production is configured for the repository owner's
verified numeric ID. Archive access retains its separate maintainer gate.

Run `npx tsx scripts/test-production-flow.ts --negative-control` from an
authenticated maintainer environment. It:

1. Requires a configured matching verifier identity.
2. Submits an explicitly labelled negative control through the ordinary API,
   consuming one daily slot, and requires a mathematical rejection.
3. Downloads that job's encrypted archive through the maintainer API and checks
   that the exact source round-trips.
4. Runs the complete Anthropic 2/3 proof against the isolated 1/3 test baseline,
   requiring both kernel replay and the publication attestation checks.
5. Checks that the public record did not change.

Job handles and results are written to a new private temporary directory. The
GitHub credential is not written. Without `--negative-control`, only the
operator-only positive replay runs. A noncompetitive pass does not exercise a
real leaderboard mutation; publication CAS is covered by mocked GitHub tests.

## Mathematical improvement attempt

The frozen upstream defines `HD λ = 2 - 1 / cStar λ`, where
`cStar λ = √2 sin θ / (cos θ + θ sin θ)` and `θ = λ/√2`.
Its unconditional fixed-scale theorem requires `0 < λ < 1` and takes the
endpoint limit to obtain the current record. Differentiation of this expression
gives `cStar'(λ) = cos² θ / (cos θ + θ sin θ)² > 0` on that range.
Thus changing only that scale approaches the existing endpoint; it cannot
produce a stronger bound. This is a mathematical screen of that family, not a
new Lean proof or a claim that other methods cannot improve the record.

The upstream 2/3 proof is complete but below the actual record. Rounding the
displayed baseline upward is not an improvement proof. No competitive candidate
was promoted, and no theorem, kernel, axiom policy, or scoring rule was weakened.

## Architecture follow-ups

The current Git-backed CAS queue is suitable for a small, bounded workload,
but it is not the design I would choose for substantial traffic:

- Admission currently creates E2B before durable queue admission. Bursty parallel
  requests can transiently allocate more workers than the final daily quota;
  process termination before cleanup can leave orphaned workers.
- Paused sandboxes hold waiting jobs. Prefer encrypted object storage at admission
  and create the sandbox only when a worker acquires the queue head.
- Use a transactional job store with per-account counters, idempotency keys,
  leases, and durable verdicts. A single persistent scheduler can finalize jobs
  promptly without browser polling or delayed GitHub cron. Keep GitHub for
  immutable accepted evidence, not as a high-frequency operational database.
- Use stable numeric GitHub account IDs for quotas and all authorization
  allowlists, with an explicit migration for existing login-derived queue keys.
- Make noncompetitive flow-test leases and results durable too; their current
  process-local/sandbox discovery approach is weaker than competitive receipts.
- Verify recoverable encrypted backup of the archive key before any key rotation.

These are identified follow-ups, not implemented migrations or proven load capacity.
